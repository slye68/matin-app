# Matin!* — Contexte du projet

Dashboard personnel du matin, application de bureau Windows, cible **Windows Store (MSIX)**, **application payante**.

## Stack technique

- **Electron** (v31) — process main + renderer, `contextIsolation: true`, `nodeIntegration: false`, bridge IPC via `preload.js`
- **HTML / CSS / JS vanilla** — pas de framework front (pas de React/Vue), un seul design system CSS (`renderer/assets/style.css`)
- **electron-store** — persistance de la config (modules activés, position/taille, tokens OAuth, préférences) dans un fichier JSON local
- **dotenv** — charge les secrets OAuth (Google, Spotify) depuis `.env` à la racine (non commité, voir `.gitignore`)
- **interactjs** — drag & drop + redimensionnement libre des cartes de modules
- **electron-builder** — packaging, cible `appx` (MSIX / Windows Store) + `nsis` en secours

## Démarrage

```bash
npm install
npm run dev        # electron . --dev (devtools ouverts)
npm run build:msix # electron-builder --win appx
```

## OAuth

- **Google** (`main/auth/google-oauth.js`) : Authorization Code + PKCE (S256), flux "loopback" RFC 8252 — ouvre le navigateur système, récupère le code via un mini-serveur HTTP local (`127.0.0.1:42813/oauth/callback`), aucune saisie manuelle. Scopes : `openid`, `email`, `calendar.readonly`, `gmail.readonly`, `tasks` (ajouté le 2026-08-06 pour le module Tâches Google — pas `tasks.readonly` : le module écrit, coche et supprime des tâches), `contacts.readonly` (ajouté le 2026-08-07 pour le module Anniversaires, People API). Refresh automatique du token côté `main.js` (`google:getValidToken`, buffer 60s avant expiration). **OAuth n'accorde jamais un scope a posteriori sur un token déjà émis** : tout compte connecté avant l'ajout d'un scope doit se déconnecter puis se reconnecter depuis Paramètres pour que le module correspondant fonctionne (sinon 403, vérifié en direct pour `tasks`) — pas une régression, juste la mécanique normale d'OAuth. Une seule reconnexion suffit à rattraper TOUS les scopes ajoutés depuis la dernière connexion (le flux redemande toujours la liste `SCOPES` complète au moment présent, `prompt: 'consent'` forcé) — pas besoin d'une reconnexion par scope manquant.
- **Spotify** (`main/auth/spotify-oauth.js`) : même schéma PKCE loopback, `127.0.0.1:42813/callback` (littéral IP imposé par Spotify, pas `localhost`). Scopes : lecture + contrôle de la lecture en cours. Refresh automatique côté `main.js` (`spotify:getValidToken`).
- Les deux flux partagent le même port (42813) mais des chemins différents ; un conflit ne peut survenir qu'en cas de lancement simultané des deux connexions (cas marginal).
- Client ID / secret dans `.env` à la racine (non versionné) — voir `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `SPOTIFY_CLIENT_ID`, `SPOTIFY_CLIENT_SECRET`.

## Décisions techniques clés

- **TheSportsDB** retenu pour les sports plutôt qu'une API payante (API-Football) — gratuit, sans clé, au prix d'un résultat parfois périmé (limite connue de la clé démo).
- **Open-Meteo** retenu pour la météo — gratuit, sans clé, pas de rate-limit agressif.
- **CoinGecko** retenu pour les cryptos — endpoints publics avec CORS ouvert (fetch direct renderer), mais rate-limit strict (~4-5 requêtes rapprochées suffisent à déclencher un 429) → un seul appel groupé `/coins/markets` pour tous les cours, cache d'historique 1h.
- **Boursorama en source PRIMAIRE du cours ETF, Yahoo Finance relégué au nom/historique/repli** (2026-08-05, `etf.js` — inversion complète de l'architecture précédente, bug réel constaté). Jusque-là Yahoo était la source primaire, avec Boursorama en simple repli si sa résolution échouait. Diagnostiqué en conditions réelles (fetches lancés depuis l'app elle-même, logs comparés à Boursorama consulté manuellement par l'utilisateur) : l'API chart Yahoo (`etfFetchYahooQuote`) avait un trou d'un jour ouvré ENTIER dans son historique de clôtures pour ces ISIN français à faible volume (un mardi totalement absent, pas un jour férié identifié) — la mécanique de repli sur "clôture la plus récente disponible" (déjà documentée pour gérer les week-ends normaux) prenait alors une référence 2 jours calendaires plus vieille que la veille réelle, au point d'INVERSER le signe de la variation journalière affichée (PAEEM : -0,45 % réel sur Boursorama, +2,4x % affiché). `etfComputeGroups` résout désormais Boursorama (`etfResolveBoursoramaPath` + `etfFetchBoursoramaQuoteCascade`) comme source du prix/de la variation pour CHAQUE ISIN, Yahoo (`etfResolveYahooSymbol`) n'étant plus sollicité que pour (1) le nom/ticker affiché (sa résolution par recherche s'est révélée fiable — seul son cours en cause), (2) l'historique du graphique même quand Boursorama fournit le prix (le scraping ne donne qu'un cours instantané), et (3) un repli complet (prix + variation + historique, avec le bug potentiel ci-dessus) si Boursorama échoue entièrement pour un ISIN — mieux qu'aucune donnée du tout. **Cascade de fetch Boursorama** (`etfFetchBoursoramaQuoteCascade`) : jina.ai Reader (`r.jina.ai/{url}`, parse le motif Markdown `"prix pct%]("` ancré sur le lien Boursorama) → allorigins.win (`api.allorigins.win/raw?url=`, parse le HTML brut comme avant) → fetch direct (dernier recours) ; pas un contournement CORS (le process main fetch déjà sans restriction), un filet contre un futur blocage bot direct de Boursorama (déjà vécu sur Eurosport, voir plus bas) — vérifié : jina.ai a suffi du premier coup pour les 2 ETFs testés, allorigins et direct n'ont pas eu à être sollicités. Chaque tentative logue systématiquement la valeur brute extraite (prix + variation, avant parsing numérique) pour pouvoir vérifier la source en cas de doute futur. **Scraper Boursorama HTML corrigé le 2026-08-04** (deux ruptures distinctes, toutes deux vérifiées contre de vraies pages, logique conservée dans `etfParseBoursoramaHtml`) : (1) l'URL de résultat de recherche n'est plus `/cours/{symbole}/` mais préfixée par catégorie d'instrument (ex. `/bourse/trackers/cours/{symbole}/` pour un ETF) — `etfResolveBoursoramaPath` matche n'importe quel préfixe ; (2) `data-ist-last`/`data-ist-variation` sont des attributs booléens SANS valeur, le prix/la variation sont le contenu texte du `<span>` (avant : `data-ist-last="32.49"`, maintenant : `<span data-ist-last>32,49</span>`) — on cible le bloc `c-faceplate__values` (le cours principal de la page) pour ne pas confondre avec d'autres instruments affichés dans le bandeau "à la une" du haut de page, qui portent les mêmes attributs.
- **Prix d'ouverture du jour retiré du bloc "Cours" ETF** (2026-08-04, sur demande explicite) — avait été ajouté puis débogué (voir historique : `meta.regularMarketOpen` n'existe pas côté Yahoo `/v8/finance/chart`, `/v7/finance/quote` qui l'expose exige une auth "crumb" non disponible ici), mais retiré de l'affichage. Le bloc "Cours" ne montre plus que le prix actuel + variation journalière.
- **Bloc "Cours" ETF : une ligne par ETF, toutes identiques** (`etf.js`, `etfCoursRowHtml`/`.etf-cours-*`) — remplace en 2 temps l'ancien affichage à un seul prix : d'abord (2026-08-05, tôt) un gros prix pour le groupe principal (`groups[0]`, le plus gros en valeur) + sous-texte, puis une mini-liste plus petite pour les autres ; jugé confus, donc re-simplifié le même jour sur demande explicite en une liste uniforme (`groups.map(etfCoursRowHtml)`, plus de traitement spécial pour un "principal") — chaque ligne : `TICKER — prix €  +/-%`, même taille/graisse pour toutes. Jamais floutées en mode confidentialité (cours de marché, pas des montants personnels — contrairement à Portefeuille/Investi/+-Value, seuls à porter `etf-money`). Le ticker court (ex. `CW8`) vient du symbole Yahoo résolu à part (`etfResolveYahooSymbol`, désormais utilisé uniquement pour le nom/ticker et plus pour le cours — voir plus haut) en retirant le suffixe de place (`CW8.PA` → `CW8`) ; repli sur le nom complet si cette résolution Yahoo a échoué. Liste plafonnée à 4 lignes visibles (`max-height`) avec scroll interne au-delà, pour ne pas laisser le bloc "Cours" grandir sans limite et déséquilibrer toute la grille du header (`.etf-header`, `align-items: stretch` — tous les blocs de la ligne s'étirent à la hauteur du plus grand).
- **Seuil de détection des trous Yahoo resserré à "≠ 1 et ≠ 3 jours calendaires"** (2026-08-05, `etf.js`, `etfFetchQuote`) — l'ancien seuil `> 3` (pensé pour ne pas signaler un week-end normal vendredi→lundi = 3 jours) laissait passer SANS AVERTISSEMENT un trou d'un seul jour ouvré : repéré en déboguant une variation "+2.47%" jugée trop élevée sur PAEEM.PA — les logs (voir ci-dessous) ont montré que le mardi 2026-08-04 était totalement absent des données Yahoo (jour ouvré normal, pas de férié identifié), donnant une référence "clôture veille" prise le lundi 2026-08-03 pour un calcul le mercredi 2026-08-05 — 2 jours calendaires d'écart, sous l'ancien seuil de 3. Entre deux clôtures sur jours ouvrés, seuls 2 écarts sont normaux (1 jour = jours consécutifs, 3 jours = vendredi→lundi) ; tout le reste indique désormais un trou et déclenche le `console.warn` existant. Logging aussi enrichi pour ce type de diagnostic : le nombre de jours d'écart avec la référence est maintenant toujours affiché sur la ligne `console.log` principale (pas seulement dans le `console.warn` conditionnel), plus un dump des points bruts du chart 5j (`short.points`) pour inspecter directement ce que Yahoo a réellement renvoyé.
- **Détection de trou de données Yahoo (variation journalière ETF)** — le calcul de `changePct` (cours actuel vs clôture de la veille, voir plus haut) suppose que le point juste avant "aujourd'hui" dans le tableau de bougies EST la veille réelle ; si Yahoo n'a pas de clôture pour un jour ouvré récent (trou de données constaté, pas un week-end — vérifié même sur une fenêtre d'1 mois, donc pas un artefact de la fenêtre courte utilisée pour ce calcul), ce point de référence remonte silencieusement plus loin, et le % affiché reflète alors un changement sur plusieurs jours plutôt qu'une vraie variation "journalière". `etfFetchQuote` logue désormais un avertissement explicite (`console.warn`) quand l'écart dépasse 3 jours calendaires (seuil choisi pour ne pas signaler un passage vendredi→lundi normal). Pas un bug corrigeable côté app — la donnée n'existe simplement pas chez Yahoo pour le(s) jour(s) manquant(s) ; se résout généralement de lui-même une fois Yahoo comble le trou côté serveur.
- **Fetch RSS via le process main** (canal IPC `rss:fetchFeed`) plutôt qu'un proxy CORS tiers — les proxies tiers testés (rss2json.com, proxy CORS générique) se sont révélés instables (erreurs 422/500/520/522). Le process main n'étant pas un contexte navigateur, aucun CORS à contourner.
